# Lantern architecture

Lantern is a small, readable 3D engine prototype written to answer one question: *what must a
small 3D platformer engine actually do each frame?* It follows Umbra's domain split (see
`umbra-audit.md`) but replaces Umbra's interfaces, injector and managers with concrete Rust types
owned by one composition root.

## Workspace layout

```text
Cargo.toml                  workspace root
crates/
  core/          lantern-core        values, IDs and handles, time, input actions, colours,
                                     logging, debug values (Umbra src/core)
  platform/      lantern-platform    backend-neutral window, device and event vocabulary
                                     (Umbra src/platform)
  sdl-facade/    lantern-sdl-facade  SDL3 context, window, event pump, gamepad, audio device
                                     (Umbra src/raylib-facade)
  renderer-3d/   lantern-renderer-3d render assets (meshes, textures), primitives, glTF/PNG
                                     loading, camera, RenderWorld packet, bitmap font, text
                                     layout and immediate-mode UI (Umbra src/renderer-2d and
                                     the UI half of src/core/user-interface)
  sdl-gpu/       lantern-sdl-gpu     SDL GPU backend: device, shaders, pipelines, buffers,
                                     textures, frame submission; private to the renderer
  physics/       lantern-physics     shapes, shape casts, collision world, kinematic character
                                     controller (Umbra src/physics)
  audio/         lantern-audio       WAV decoding, sound bank, software mixer (new)
  scripting/     lantern-scripting   Nyx host: script loading, engine API, hook calls (new)
  debug/         lantern-debug       debug HUD panel and debug-draw helpers (Umbra src/debug)
  engine/        lantern-engine      frame loop, fixed-step schedule, input routing, world
                                     (entities, transforms, hierarchy), scene stack, state
                                     machine, render extraction (Umbra src/engine)
  nyx-sys/       nyx-sys             raw Nyx C ABI bindings (existing)
  nyx/           nyx                 safe Nyx wrapper (existing)
apps/
  platformer-game/                   the demo game and composition root (Umbra src/snake-game)
    scripts/                         Nyx gameplay scripts
assets/                              sounds, textures, meshes (generated by tools/asset-gen)
```

### Dependency direction

```text
                  lantern-core
      ┌──────────┬────┴──────┬─────────┬──────────┬───────────┐
  platform   renderer-3d   physics    audio     scripting(nyx)
      │          │  │
  sdl-facade  debug  engine (core, platform, renderer-3d)
      │          │
   sdl-gpu (renderer-3d, sdl-facade)

apps/platformer-game depends on all of them and is the only place they meet.
```

No library crate depends on `lantern-sdl-facade` except `lantern-sdl-gpu`, so SDL types
never reach engine, physics, audio, scripting or game code. The game calls the GPU backend
with `renderer-3d` types only (`RenderWorld`, `MeshData`, `MeshHandle`).

## Umbra → Lantern mapping

| Umbra | Lantern | Notes |
|---|---|---|
| `Core::IApplication` + `Engine::Application` | `lantern_engine::frame_loop::run` + the `Game` trait, implemented by `PlatformerGame` | The loop is a function, not a base class. The game owns its subsystems. |
| `DependencyInjector` registrations | plain construction in `apps/platformer-game/src/main.rs` | Field order of `PlatformerGame` is the shutdown order. |
| `IWindow`, `IInputBackend` + Raylib facades | `lantern_platform` events + `lantern_sdl_facade::{SdlContext, SdlWindow, SdlEventPump}` | The engine loop sees the platform through one small trait, `PlatformBackend`, so tests can drive it with a fake clock. |
| `SystemManager` / `GameSystemManager` | fixed, documented call order inside `PlatformerGame::fixed_update` | Order is code you can read, not registration order. |
| `SceneManager` + `Scene` | `lantern_engine::scene::{SceneStack, SceneCommand}` + `World::despawn_scene` | Every entity is tagged with the scene that spawned it, so exit removes exactly those. |
| `EntityManager` + component pipelines | `lantern_engine::world::World` with `EntityId` (generational) and typed stores | Iteration is in slot order, so it is deterministic. |
| `IGameState` + `StateMachine` | `lantern_engine::state::StateMachine<S>` with an enum of game states | Transitions are values returned from `update`. |
| `ActionSet`, `KeyMap`, `InputDispatcher`, `ActionRouter` | `lantern_core::input::{ActionSet, Bindings, InputSnapshot}` + `lantern_engine::input::InputRouter` | Keep named actions and pressed/released edges. Replace event-bus callbacks with an immutable snapshot that fixed steps read. |
| `IRenderComponentManager` | `lantern_engine::extract::extract_render_world` | Produces a `RenderWorld`; the renderer never sees gameplay types. |
| `IRenderer` + Raylib renderer facade | `lantern_sdl_gpu::GpuRenderer` | One concrete backend. A trait is added only when a second backend exists. |
| `renderer-2d` | `lantern-renderer-3d` | Forward renderer: one lit textured pipeline, one line pipeline, one overlay pipeline. |
| `physics/collision` | `lantern-physics` | 3D shape casts and a kinematic controller, no rigid bodies. |
| `debug` + `core/debug` | `lantern_core::debug::DebugValues` + `lantern-debug` | Same path-keyed tree (`"Player/Velocity"`), drawn through the text/UI path. |
| `core/user-interface` + `snake-game/ui` | `lantern_renderer_3d::ui::Ui` + `apps/platformer-game/src/ui` | Immediate-mode labels and buttons with focus navigation. |
| (none) | `lantern-audio` | Mixer is pure Rust, the SDL audio stream lives in the facade. |
| (none) | `lantern-scripting` | Nyx owns game rules; Rust owns the controller and collision. |
| `snake-game` | `apps/platformer-game` | Game rules, content, scripts and composition. |

## Conventions (stated once, tested in `lantern-core`)

| Topic | Convention |
|---|---|
| Handedness | Right-handed. |
| Axes | +Y is up. -Z is forward. +X is right. |
| Units | 1 world unit = 1 metre. Time in seconds. |
| Angles | Radians in code. Anything in degrees is named `_degrees`. Yaw rotates about +Y, positive is counter-clockwise seen from above. |
| Vectors and matrices | `glam` column vectors and column-major matrices. A point is transformed as `matrix * point`. |
| Transform composition | `local = translation * rotation * scale`. `world = parent_world * local`. |
| Clip space | SDL GPU's clip space on every backend: NDC y up, depth 0 (near) to 1 (far). Projection is `Mat4::perspective_rh` (0..1 depth). Depth test is `LESS`. |
| Texture UV | (0, 0) is the top-left texel; v grows downward. Row 0 of uploaded pixels is the top row. |
| Winding | Counter-clockwise triangles are front faces. Back faces are culled. |
| Colours | Linear `f32` RGBA in code. The swapchain is presented as it is configured by SDL (sRGB not forced). |

## Timing

`lantern_core::time::FixedStepClock` implements the proposal from Umbra's
`game-loop-architecture.md`:

- fixed step: 1/60 s;
- each display frame adds the measured time (clamped to `MAX_FRAME_TIME` = 0.25 s) to an
  accumulator;
- times within 0.2 ms of the step are snapped to the step (vsync jitter);
- at most `MAX_STEPS_PER_FRAME` = 8 fixed steps per frame, after which the remaining backlog is
  dropped and counted in the HUD;
- the remainder gives `alpha = accumulator / step` for render interpolation.

Simulation (controller, gravity, jumping, moving platforms, scripts) only runs in fixed steps
and only sees `FIXED_STEP`. Nothing in the simulation reads the frame delta.

## Input

1. The platform pump turns SDL events into `PlatformEvent`s (key down/up by `KeyCode`, mouse
   motion and buttons, gamepad buttons and axes, window events).
2. `InputRouter` keeps device state (keys held, mouse delta, gamepad axes) and, once per display
   frame, evaluates `Bindings` into an `InputSnapshot`: for each action, whether it is held, was
   pressed or released, and its axis value.
3. Pressed and released edges are *latched* until a fixed step consumes them. If a display frame
   runs zero fixed steps, a jump press is not lost; if it runs three, only the first sees the
   press. Mouse look is accumulated and consumed by the frame update, since the camera is a
   presentation concern.

## Per-frame sequence

```text
display frame
├─ platform.pump_events()            SDL → PlatformEvent (quit, resize, minimise, input)
├─ input_router.begin_frame()        PlatformEvents → device state → InputSnapshot
├─ clock.advance(now)                accumulator += dt, returns N fixed steps and alpha
├─ repeat N times: game.fixed_update(snapshot)
│   ├─ world.store_previous_transforms()       for interpolation
│   ├─ scripts: OnFixedUpdate(dt)              Nyx rules: pickups, triggers, platform paths
│   ├─ apply script commands                   spawn, despawn, move platform, sound, scene
│   ├─ moving platforms step                   kinematic movers, record their velocity
│   ├─ character controller step               input → velocity → move-and-slide → grounded
│   ├─ triggers and reset volumes              overlap tests → script events
│   └─ world.update_world_transforms()         hierarchy, parent before child
├─ game.frame_update(frame)          camera orbit/follow with collision, UI, HUD values
├─ game.render(alpha)
│   ├─ extract_render_world(world, alpha)      interpolated transforms → DrawItems
│   ├─ debug draw lines, UI overlay quads      HUD and menu text
│   └─ gpu.render(&render_world)               upload, passes, submit, present
└─ audio.pump()                      mixer → SDL audio stream (keeps ~60 ms queued)
```

## Ownership and shutdown

`PlatformerGame` owns, in field order: scripting host, audio output, mixer, GPU renderer,
world, physics world, UI state. Rust drops fields in declaration order, so the struct is laid out
so that scripts (which may hold sound handles by name) go first and the GPU renderer is released
before the SDL window, which is owned by `main` and outlives the game. `SdlContext` is created
first in `main` and dropped last, which calls `SDL_Quit`.

GPU resources are owned by `GpuRenderer` in slot maps addressed by generational handles. Meshes
and textures released during a frame are queued and destroyed after the GPU has finished the
frame that used them (`wait_for_idle` on release in this prototype; see `future-work.md`).

## Rendering

- One vertex format: position (vec3), normal (vec3), uv (vec2), colour (vec4).
- Pipelines: lit opaque (texture × vertex colour × material colour, one directional light plus
  ambient), debug lines (no depth write), overlay (alpha-blended screen-space quads sampling the
  font atlas).
- The game builds a `RenderWorld` every frame: camera, light, `DrawItem { mesh, texture,
  transform, colour }`, debug lines and overlay quads. The backend sorts opaque items by
  pipeline, then texture, then mesh, and culls them against the camera frustum.
- Depth texture recreated when the swapchain size changes. Zero-sized drawables (minimised
  windows) skip rendering.
- Debug builds create the SDL GPU device with validation enabled.

## Scripting plug-in point

`lantern-scripting::ScriptHost` owns the Nyx runtime. In each fixed step, after input and
before physics:

1. the host calls the mounted application's `OnFixedUpdate(dt)`;
2. Nyx calls engine functions (`Input.IsPressed("jump")`, `Entity.Position(id)`,
   `Sound.Play("pickup")`, `Game.Reset()`, `Log(...)`); reads answer from a per-step view of the
   world, and writes become `ScriptCommand`s;
3. after the call, the game applies the queued commands in order.

Scripts never get pointers: entities are passed as `i64` IDs that are checked on every call.
Errors are logged with file and line and shown on the HUD; a failing hook does not stop the game.
`OnStart` runs when the gameplay scene is entered and `OnExit` when it is left. Events from Rust
(`OnPickup`, `OnTriggerEnter`) are delivered after physics in the same fixed step.

## Translation notes for a simpler language

- **RAII / Drop**: GPU resources and SDL objects free themselves on drop. A language without
  destructors needs explicit `destroy` calls in the order documented in "Ownership and shutdown".
- **Generational handles**: a `(index, generation)` pair; any language can do this with two
  integers and a check on lookup.
- **Enums with data**: `PlatformEvent`, `SceneCommand` and `ScriptCommand` are tagged unions.
- **Traits**: only `PlatformBackend` (for tests) and `Game` (the loop's callback) are traits.
  Both can be a struct of function pointers.
